Part 2 · Working with agents
2.1

Trust comes before parallelism

Ten agents you don't trust give you ten times the unchecked work, and you become the bottleneck. Make one agent trustworthy first. Then running many is easy.

  • Unchecked work compounds. Agents copy the patterns they find, so one bad pattern gets copied by the next ten agents. Delete bad patterns before they spread.
  • Trust needs three things: a goal that can be checked, evidence that it was met, and a trail of what was decided and why.
  • Your job shifts from writing code to designing checks and reading evidence.

Checkable goalWhat does done mean?The done check in every prompt, asked for by the guidelines and the per-prompt hook
EvidenceHow do I know it's done?Proof on the real artifact, through the project's verify-<app> skill
TrailWhat did it decide, and why?The decision log from show-me-your-work
RememberIf you want to go fast, go deep first.
2.2

Say the goal, not the ceremony

A prompt needs at most five things, one sentence each: the goal, a done check that can pass or fail, the proof you want to see, what you already know, and the real constraints.

  • Leave out the how. Say what to achieve and leave room for a better path than the one you'd pick.
  • Leave out your theory, at first. A stated guess narrows the search to wherever you pointed. Give the fact ("/ws returns 403"), not the "so..." after it.
  • Restate noisy reports first. A misreading caught in the restatement costs one message instead of one wrong fix.
  • Don't list skills. The playbook already sequences them, and a hand-written sequence drops steps it would have kept.
  • A done check must be able to fail. "Make it better" and "work on it for an hour" aren't checks.
BEFORE

"see if there's a way to fix this." A proposed fix counted as done. Runs still didn't show up.

AFTER

"done means you show a run appearing through the Coder URL, or name every blocker. show me /ws status and the /api/runs body. read-only for now."

Try it:

/flatpaper-stack:flatpaper-mode read this thread. restate the underlying issue in plain words. don't change any code yet.

2.3

One front door

When the model picks skills by matching descriptions, it gets fuzzy as skills overlap. A router is predictable: one entry point matches a playbook, copies its steps into a task list, and calls each skill when a step needs it.

  • A skipped step stays visible as skip: <reason>, so you can see what the agent chose not to do.
  • Your words carry the intent and the playbook carries the rigor, so follow-ups can be short: "continue", "do it", "raise a draft PR".
  • When the subject changes, the work should re-match. A mode mid-feature otherwise treats your new question as the next feature step.
  • Give parallel work its own worktree. Agents sharing one working tree fight over files, ports, and build output.

In flatpaper-stack: flatpaper-mode, its 16 playbooks, the shared Start and Finish steps, re-matching on every prompt, and a worktree for every writing subagent.

2.4

Understand before you change

Agents fail in two ways: they misread what you want, or they lack the context to do it right. An agent that edits without a traced model fixes the symptom at the first plausible spot. Tracing first is cheaper than the second bug.

  • Investigate read-only first, and ask what data it used, so evidence separates from guesses.
  • Ask it to convince you. An agent that has to explain must back each claim instead of stating it and moving on.
  • Turn explanations into claims, predict, then run: explanation → claims → predictions → run → compare. A vague prediction can't be wrong, so it teaches nothing.
  • When a result surprises you, suspect the check first.
  • "Nobody wrote down why" is itself an answer. Code is not evidence of its own intent.

Try it:

/flatpaper-stack:flatpaper-mode investigate why background jobs time out every few hours. give me what we know, what data you used, and your best hypotheses. don't change any code yet.
/flatpaper-stack:why was the retry limit set to five? does the reason still hold?

In flatpaper-stack: the Investigation, Runtime forensics, and Trace forensics playbooks, why, recall, Session pickup, and the confidence tiers in principles.md.

2.5

Settle the design by running something

One attempt at a hard design locks in the first shape the model thought of. Plan through code: prototypes answer the open questions, a README sets the target for shared code, and the written plan comes last.

  • Never take the first design. Ask for a few, and pick from evidence you can see.
  • Don't spend reviewers on an abstract plan. Review of a plan with no code behind it invents risks that never happen.
  • Different models have different blind spots, so a finding two of them raise independently is a strong signal.
  • For a migration, say "the result must match the original exactly, bugs included". Otherwise old and new can't be compared.

Most changes need none of this. flatpaper-mode applies the ladder on its own; reach for these directly when you want more or less scrutiny.

2.6

Pin it, build it, clean it

Say what you observed and let the playbook demand the evidence. Every build task pins something before anything changes.

PerfA measured baseline1.8s on this fixture. before and after

The sabotage test

If every function returned None, would this test notice? A test that passes when the code does nothing is hollow.

PASSES WHEN BROKEN

send.assert_not_called() after notify_user(42). Code that does nothing never calls send.

FAILS WHEN BROKEN

Notify an opted-out user and a subscribed one, then send.assert_called_once_with(7, ...).

Write the failing test first when there's a cheap test path. Don't force one through brittle mocks when running the real command is stronger evidence.

Clean before review

Cleanup is not optional polish. Narrating comments and defensive dead weight read as unfinished, and the extra code is where the next bug hides. Clean code and prose separately, and have comments reviewed by an agent that didn't write them, because authors defend their own.

2.7

Prove it on the real thing

"It compiles" is not evidence. Verification is the step that usually waits on a human. Make the agent able to do it, and you stop being the bottleneck.

  • Match the check to the change. A CLI runs the real command. A UI walks the flow in the running app. A parser replays a saved input. Perf compares profiles. Storage reads the value back.
  • Presence is not behavior. "Installed", "running", or "returned 200" can all pass while the user is still blocked.
  • Vet every number. A warm cache, an untuned side, or work outside the timed region can fake a speedup. Ask "why not double?" and answer from a run.
  • The judge is never the author. Review and verification go to an agent that didn't write the change.
  • A verification skill is infrastructure. Commit it so every person and agent drives the app the same way, and keep its feature map honest as the app changes.
ALL GREEN, NOTHING THERE

Dashboard loaded. Daemon restarted. WebSocket 101. /api/runs returned 200, with body [].

THE REAL CHECK

A smoke run actually appears in the dashboard through the Coder URL.

2.8

Earn the loop before you leave it

A loop you don't trust produces unchecked work faster. What makes leaving safe is a checkable finish condition, an isolated worktree, and a decision log you audit later.

Four checks before a run goes alone

  • You've done the task once, or watched it done.
  • The agent has your tools: the verify skill, logs, profiler.
  • Every stage proves its work and can stop the line.
  • You've read transcripts and turned repeat failures into checks.

The handoff

/flatpaper-stack:flatpaper-mode im going to bed. migrate every caller to the new parser in a fresh worktree off main.
done means zero old callers, all parser fixtures pass, old api deleted.
keep a decision log. don't ask me before committing.
/loop until done. if you're truly stuck after a few hours, stop and write up why.

Each line buys something: a switch from asking to deciding, checks every iteration can run, isolation, a pre-answered permission, and an escape hatch that beats hours of creative goal reinterpretation. A duration is not a finish condition.

  • Each iteration makes one change, runs one check, writes one log row. Changes that didn't help are discarded.
  • A plateau means pivot, never relaxing the finish condition.
  • Ask when watched, decide and log when away. The log is what makes deciding safe.
  • In the morning, audit decisions, not the whole night. Read the Attention section first.

In flatpaper-stack: the Autonomous run, Pause safely, and Session pickup playbooks, show-me-your-work, and ketchup.

2.9

Hand off work, keep the judgment

A subagent starts with no chat history and can't ask you a question. It works only from its brief, and you still own whatever it hands back.

  • Delegate to keep the main thread small. Bulk reading, independent slices, and fresh review go to subagents. The main thread keeps the summaries and the decisions.
  • Write a brief a stranger could run. Goal, scope, context, acceptance, verify commands, timebox, what's forbidden, and the report shape. A field you can't fill is a unit you haven't scoped.
  • Keep code on the session model. Don't split one change into a planning agent and cheaper writers. To write a plan detailed enough for them, the planner writes the code itself. The split then costs more, and one bug in the plan reaches every writer.
  • Mix models only where a skill says to. swarm, arena, interrogate, reflect, why, and recall pick their own models. Everything else runs on the session model.
  • Read the diff yourself. A subagent's report is a claim. Check its work and write your own summary.
WorkWho does it
One change, step by stepOne agent on the session model
Independent slicesParallel workers on the session model, each in its own worktree
Races, model panels, and bulk reading inside those skillsThe models each skill names
ReviewA fresh agent that didn't write the change

In a four-task pilot on this repo, with one run per setup, an Opus planner with Sonnet or Opus writers never beat one Opus agent working alone. The planner alone wrote more Opus output tokens than the solo agent did, total agent time doubled, and one bug in the plan showed up in every setup that used it.

2.10

Steer with names

Say a principle's name and the agent applies the full rule it already read. One phrase redirects the work more precisely than a paragraph.

SayWhen
prove it worksIt claims done because the build passed
fix root causesIt's silencing a symptom
attack the premiseTwo fixes sharing one premise have failed
build the leverIt's doing repeated work by hand
subtract before you addIt's bolting a new piece onto old ones
separate before serializing shared stateTwo attempts are about to write to one branch

The agent must say which decision the principle changed. A name with no decision behind it was name-dropping. Every turn ends with a Principles that changed decisions footer, or "none this turn", so a missing footer shows the agent has drifted from the mode. Don't memorize the list; come back when an agent does something a name would have prevented. All 24 are in Part 3.

2.11

Fix the repo, not the prompt

When you correct agents for the same mistake again and again, the fix belongs in the repo, not in your next prompt.

The fix ladder, strongest first

  1. Make the mistake impossible with architecture or a better data structure.
  2. Block it with types, or a lint whose error names the fix.
  3. Catch it with a test.
  4. Write it down as a rule. Nothing fails when a rule is skipped, so this comes last.
  • Human review isn't on the ladder. A reviewer who catches the same mistake on every PR is the problem.
  • Start smaller than you think. Add a skill or a check when the same failure shows up twice.
  • Approve a lesson only if it would change a future decision. One odd session is an anecdote.
  • Don't edit a skill mid-task. Fix it in its own change.

"straight to the point" appeared in 54 of 1,951 prompts despite a written rule saying "concise". A rule nothing enforces shows up as a repeat. In flatpaper it became a per-prompt hook.

In flatpaper-stack: correct, reflect, the hooks, and check-skills.sh and test-scripts.sh, run in CI on every push.

2.12

Keep a map the agent reads first

An agent that starts cold re-traces the system every session, and a diagram nobody updates turns into a confident lie.

  • Read. Every playbook reads the map before tracing code, and trusts the code where they disagree.
  • Update. A change that moves a boundary the map shows updates it in the same PR.
  • Verify. Pin it to a SHA and release, and fact-check it row by row like code.
  • Drift. A script says at session start when the map is behind.

In flatpaper-stack: the Architecture page playbook and arch-drift.sh.
