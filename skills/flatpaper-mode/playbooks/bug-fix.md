### Bug fix

**You own this task. Plan, review, verify.**

Every shipped line traces to runtime evidence. A change that "might help" is a hypothesis, not a fix. When evidence refutes a hypothesis, revert what it motivated.

1. Name the correct final state and the broken final state, one line each. A loading state, an expected dialog, or a setup step is not the bug. The two states must be observable on the surface where the bug happens.
2. Check for an existing fix with `git log`, `gh pr list --search`, and the issue. If a PR or commit already claims it, verify it instead of writing a new one. Run the baseline (the PR's base, or the commit before the fix) and the patched build, twice each, with the same environment and data. It is confirmed only when the baseline shows the broken state twice and the patched build shows the correct state twice. Report confirmed, insufficient (the baseline never showed the bug twice), or inconclusive (a run could not complete), and stop. A claim in a thread without a PR or commit is not a fix.
3. Reproduce it yourself on that surface (CLI, browser, workspace, pipeline). Use the project's `verify-<app>` skill if one exists. If it won't reproduce directly, synthesize the trigger, tighten the conditions, or add instrumentation until it fires. Synthesizing means building the real inputs or timing that cause it, not editing state to fake the result. The broken state must appear twice, with state reset in between. No baseline exists until it does. State inspection may confirm what you observed. It must not inject or force the symptom. Ask the user to reproduce only with a specific reason you cannot reach the surface.
4. Find the cause by elimination. Seed the hypotheses from the code trace and the regression history (`git log -S`, `git blame`, recent changes to the area). Each pass, test the split that cuts the most remaining problem space, and rule it out with runtime evidence (logs, instrumentation, real responses). When the cause lives in a running process, instrument it per `runtime-forensics.md`. When all you have is a captured trace or dump, read it per `trace-forensics.md`. When the bug is a race or a wrong order of steps and the area has a TLA+ model, run the `statechart` skill to read each violation as a path of states. Don't stop at the first plausible cause. The symptom must fully disappear once the surviving cause is removed.
5. If there is a cheap local test path, write a test that fails on the broken state and commit it now, before writing the fix, so history shows the failure first. Skip when the test would need brittle mocks, and say so. Running the real command is stronger evidence.
6. Write the smallest fix the evidence justifies. If it crosses a module boundary, sketch the shape first, per the Feature playbook.
7. Verify on the same surface, twice, with state reset in between. The original repro now ends in the correct state. Unit tests show branch behavior, not bug absence. "Inconclusive" or a different surface is not a pass. Say so.

**Reply:** what was broken, the root cause, the fix, and how you verified it. Paste the failing and then passing repro output verbatim.
