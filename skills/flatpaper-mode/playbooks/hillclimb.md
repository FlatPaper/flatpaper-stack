### Hillclimb

**You own the metric and the integrity of the experiment. Delegate the attempts, then review and measure each one yourself.**

For a sustained climb on one measurable thing toward a target ("hillclimb", "push this metric up", "iterate until X%"). The metric can be an eval score, a bundle size, a pass rate, or a latency. A one-off fix is Bug fix or Perf.

1. Ground the workload, then build the case, the harness, the baseline, and the log. Run the `how` skill over the target. If you cannot spawn its explorers, trace the target by hand and log that. Name the workload dimensions that can move the metric, such as data size, history, state, and concurrency. Then run Perf steps 1 to 4 (`playbooks/perf.md`). They apply to any metric. Read Perf's "complaint" and "symptom" as the target metric and how it scales with the workload. For an eval score, the harness is one Eval run (`playbooks/eval.md`), and its prompt, rubric, and judge prompt are harness files. Work on one branch, the one the PR comes from. The check is each dimension named with the code path it moves, the baseline row in the log, and `harness.sha256` on file.
2. Write the stop predicate as a log row. It adds a floor on attempts to Perf step 1's target, so a lucky early win cannot end the run, for example "at least 30% faster and at least 8 attempts". Every attempt counts toward the floor, kept or reverted. For a deterministic metric, the predicate also carries Perf step 1's minimum gain worth keeping. The check is the predicate row in the log.
3. Ground each hypothesis in a mechanism from step 1, such as "defer X off the boot path because it blocks first paint", not "try memoizing something". A perf metric is time, memory, size, or cost. Order its hypotheses by the mantras in Perf step 5, and log each mantra you skip. Use only their order, not that step's stop rule. Moving to the next mantra counts as a change of category in step 6. Order the hypotheses for any other metric by the measured profile of where the metric goes, such as the failure classes that cost a pass rate the most. The check is a named mechanism in each attempt's row.
4. Run one hypothesis per iteration: one change, one measurement, then keep or revert. Never stack untested changes, and never claim a win from reading the code (prove it works). Each iteration ends in its check before the next begins (sequence verifiable units). The run is unattended when no user turn is expected before the stop. Then use `/loop` only as the wake, and re-check the predicate on each wake.
   - Delegate the change with a tight scope. Spawn `subagent_type: "flatpaper-stack:flatpaper-agent"` with `isolation: "worktree"` and no `model`, briefed per `../references/subagent-brief.md`. Review its diff instead of typing it (guard the context window). If you cannot spawn, because you are a subagent or the Agent tool is missing, make the change yourself in a worktree for that attempt (`git worktree add`). The same rules apply.
   - Cherry-pick the change onto your branch, and measure it with Perf step 4's keep rule. Perf step 6 adds the `architect` skill when an attempt crosses a function boundary. Perf step 7 adds the sqlite diff when an attempt needs a profile comparison. Perf step 8's switch to Hillclimb does not apply here.
   - A tweak that "might help" is not kept. Log the row either way.

   The check is a matching checksum before each measurement, one log row per iteration, and a clean tree before the next iteration.
5. Explore in parallel, but measure serially. When several hypotheses are independent, the `swarm` skill may explore them at once, each in its own worktree: profiling, reading, and prototypes (separate before serializing shared state). Every number you keep comes from a serial run on the frozen harness, because parallel runs share the machine. The check is that no kept row cites a number from a parallel run.
6. Push past the first plateau. After 3 reverts in a row, log a pivot row before the next attempt. Then change category, combine near-misses, reread the source, or try something more radical before you conclude that no gain is left. Correctness and simplicity outrank the number, so keep a simplification that holds the number (laziness protocol). The check is a pivot row after each run of 3 reverts.
7. Stop when the predicate is met, its floor on attempts included. Until then, don't quit while cheap untried hypotheses remain. Stop short of the predicate only when the ideas left are marginal and the target looks out of reach. Then say so with the limiter. Never relax the predicate to meet it. If you are stuck, say so instead of spinning. The check is the stop row, with the predicate state, the limiter, and the predicate text unchanged from step 2.
8. Run the `show-me-your-work` audit and fresh review over the log. If you cannot spawn the reviewer, record `BLOCKED: independent review`. Then run Opening a PR (`playbooks/opening-a-pr.md`) with the kept commits in the order they landed. Put the baseline and final numbers under Verification. The check is the Attention section, and a PR whose commits match the kept rows of the log.

**Reply:** the metric and target, baseline to final as median and range with the percent delta, the limiter, the iterations run (kept and reverted), each kept change on one line, the decision log path, the Attention section, and the best idea you would try next.
