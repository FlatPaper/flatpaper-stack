### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns ("run this whole project", "own this migration until it lands"). One task driven to a predicate is Autonomous run. A queue of PRs the user lands is Autopilot stack. One ambitious run that needs a bespoke workflow is `figure-it-out`. Work that one agent could finish inside the session's budget is not a program.

Run it with your own tools. Spawn workers with `Agent`. Keep the program's state in a store under `~/.claude/orchestrate/<slug>/`, outside the repo, with `notes.md` as its tracker. Call no scripts, and never relay messages or status between agents.

#### Arm the program

- **The user's go comes first.** State the goal, the first unit, and the size of the program, which is the owners you expect and the verifier per PR. A request to state the plan is not a go. A request to run the program is the go for up to three owners. A request to orchestrate a plan that lists its PRs names the program's size, so it is the go for that plan. A larger program waits for the user's go on its stated size, unless the request already named it. The go grants owners the merge of their own PRs inside the program's scope, and nothing else.
- **On the go, write the full program objective into `notes.md`** and restate it in your todolist, so it stands across turns until the program is done. If a Multi-phase plan names this playbook, the objective is the text its plan names. Start a decision log with the show-me-your-work skill in the store. Only you write `notes.md` and the log.
- **Arm `/loop` as a long fallback heartbeat,** about an hour. Agent completion notices are the main wake signal. Its prompt names this file's absolute path and the store's `notes.md`. Each tick re-reads both, records any unreported head or unrecorded agent, and judges every agent by its pushes and PR activity. A tick that changed something ends with a catch-up per the `ketchup` skill. A tick that changed nothing stays quiet.

#### Topology

- **One owner per PR.** Each owner is `subagent_type: "flatpaper-stack:flatpaper-agent"` with `isolation: "worktree"` and `run_in_background: true`, briefed per `../references/subagent-brief.md`. The brief opens with `ROLE: orchestrate owner` and the path of this file. The owner carries the PR from build to merge. Its first step is `git fetch origin && git switch -c <branch> origin/<base>`, because the worktree starts at your HEAD. It runs Opening a PR and Babysit for its own PR, then merges it per the verifier rule below. Its FORBIDDEN field allows a rebase of its own branch, a `--force-with-lease=<branch>:<sha>` push pinned to the SHA it last pushed, and `gh pr ready` and `gh pr merge` of its own PR on its verifier's pass. It forbids auto-merge, admin merge, any push to another branch, and the merge of a PR its plan marks review-gated. Only the owner pushes, rebases, or retargets its branch. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners. If the PR gate blocks its `gh pr create`, it reports `BLOCKED: pr-gate`, and you ask the user to restart the run with `FLATPAPER_PR_GATE_OFF=1`.
- **A fresh worker for each independent task.** Brief it per `../references/subagent-brief.md`, with each upstream report it depends on pasted in full. Give each writer its own worktree, and run runtime checks through the project's `verify-<app>` skill, per flatpaper-mode's Driving the app section.
- **A sub-coordinator only when one area has many parallel workers.** It owns that area's workers and briefs and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers. Keep about ten workers in flight per coordinator, and start the next one as each finishes instead of waiting on a whole batch.
- **When new work needs a worker's built state,** such as its checkout or uncommitted changes, start a fresh worker in that worker's worktree. A fork copies the coordinator, not the worker. Message a worker only for a follow-up on the same work, never to check on it.
- **Each PR gets a verifier that isn't its owner, on a different model.** The owner spawns it at the code-ready head with `model` set to whichever of `opus` or `fable` the owner is not running on. It reruns the gates, proves the load-bearing behavior on the real surface through the `verify-<app>` skill, and audits the diff against the PR body. Its brief forbids GitHub writes: no approval, comment, or merge. On its pass, the owner follows Shipping (`shipping.md`) step 6 for its own PR, with `--match-head-commit` pinned to the head the verifier passed. That step marks the PR ready, waits on its checks, including on a repo with no required checks, reads the base, head, and review state with its stop rules, merges, and reads the merge back. Check the pre-merge read and the read-back that Shipping step 6 names. A PR its plan marks review-gated stops at merge-ready for the user, and its owner never merges it. A PR whose patch loosens a gate, such as a skipped test or a relaxed lint rule, needs your countersign in the decision log before its owner merges, as in Autopilot-full (`autopilot-full.md`) item 4. A stacked PR merges only after its base PR has merged and the owner has rebased it onto trunk. Babysit still stops at owner-green, so the merge is this playbook's step, not Babysit's. A new head needs a new pass. Never give or bypass an approval GitHub enforces. A PR that needs one waits for it, and the owner reports the wait.
- **Start with one unit.** Take it through brief, owner, verifier, and merge before you fan out, so a flaw in the brief costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **If you can't name the evidence that proves a unit done, the unit isn't scoped yet.** Every brief fills the fields in `../references/subagent-brief.md`.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA. Read a sample of each sub-coordinator's briefs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups in `notes.md`.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks`, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text. Stop it, confirm the stop, and run `git worktree remove --force <its worktree>` before a replacement checks out its branch at the last pushed SHA. Retry by cause: a smaller scope after a context limit, the same brief after a dropped connection, and a different `model` after a tool error. After two retries, drop the unit, log why, and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action outside the merge grant, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.
- **Stand down at once on the user's stop.** Stop every owner and confirm each stop, so no write or merge lands after the hold. Record where each one stood in `notes.md`. Spawn replacements only when the user releases the hold.

**Reply:** catch the user up per the `ketchup` skill: what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, the decisions waiting on the user, and the store path.
