### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until agents that never wrote its code have proven the exact head that lands.**

For a queue of changes the user hands off to build, verify, and merge unattended ("autopilot and merge", "run the queue to merged"). Run the Autopilot stack playbook (`autopilot-stack.md`) with the replacements below, in its step order. "Stack step N" means that playbook's step N. Its owners count as Autopilot stack owners wherever another playbook names one, and they also merge their own PRs.

1. **In stack step 1, the user's go grants the merges.** The go is required, and the grant covers only the queue's items. An item the user names as theirs, a PR its plan marks review-gated, and any PR outside the queue stop at owner-green for the user. A request to state the plan is not a go. Check that the log records the go and the items it covers, and that no review-gated PR merged.
2. **In stack step 2, the owner may merge its own PR.** The brief opens with `ROLE: autopilot owner` and the path of this file. Its FORBIDDEN field also allows `gh pr ready` and `gh pr merge` of the owner's own PR under items 6 and 7 here. It still forbids `gh pr merge --auto` or `--admin`, and any push to another branch. For an item that stops at owner-green under item 1 or item 4, the FORBIDDEN field forbids `gh pr ready` and `gh pr merge` as in stack step 2. When an item 4 stop arises after the spawn, send the owner a stop in place of a verdict, and the owner holds at owner-green. Check each brief's FORBIDDEN field against this before the spawn.
3. **In place of stack step 3, run owners in parallel off trunk, never stacked,** so each PR lands on its own. Every owner's base is trunk. A PR that needs another item's code starts after that item merges, from the new trunk. Check that every PR in the queue reads trunk in `gh pr view <n> --json baseRefName`.
4. **In stack step 5, your countersign can be the approval.** A grant covers approvals only when the user's go names approvals explicitly. Under such a grant, your countersign is the approval. The owner's record of the approval points at your countersign, so a verifier can check the countersign. Without that grant, a PR that loosens a gate stops at owner-green for the user, and you send its owner a stop, never a verdict. Neither case covers an approval GitHub enforces. Before you send a verdict, check that every loosened gate in the PR has your countersign in the log. Where a countersign stands in for an approval, check that the logged go names approvals.
5. **In stack step 6, the heartbeat prompt names this file and `autopilot-stack.md`,** and says only the queue's items merge, each on a verdict that names its exact head SHA. `/loop` stays a long fallback heartbeat, and agent completion notices stay the main wake signal. Check that the armed prompt names both files.
6. **In place of stack step 7, prep each merge on the trunk it lands on.** Items 6 to 9 here replace stack step 7. Once the swarm's lanes have started, the owner rebases onto current trunk, pushes with its lease, reports the new head and patch-id, and waits for green CI. Green CI alone never authorizes a merge. The merge-prep head is a new head, so it gets one fresh verifier per stack step 4 before it merges. Send the owner your verdict with `SendMessage`, naming the one head SHA it covers, only for a PR that no item 1 or item 4 stop holds. For a held PR, send a stop instead. The owner merges only that exact SHA. It matches against your message, not a log row, and any other head needs a fresh verdict from you. Before you send a verdict, check that it names the head SHA the owner last reported. Before the owner merges, it checks that its current head is the SHA your message names.
7. **Judge the trunk move right before merging, then merge.** The owner fetches trunk and asks whether its changes can affect the patch, because rebasing for every trunk move never ends.
   - Rebase and wait for CI when the code that would land was never tested. That covers a conflict (`git merge-tree --write-tree origin/<trunk> HEAD` exits 1), a file both sides changed, and a change to which checks run for the PR. Any rebase here makes a new head, so it needs a fresh verdict per item 6 before the merge.
   - A lockfile both sides changed needs no rebase when two things hold on the merge result. A frozen install, such as `npm ci`, passes there, and the packages the PR changes resolve there as they do on the head. That install tests the lockfile that would land. A failing install means the rebase must repair the lockfile.
   - When trunk changed a caller of the patch, or code or a dependency version the patch relies on, run the patch's checks on the merge result. Merge on a pass. The merge result is a local merge of the head into current trunk.
   - Otherwise merge.

   To merge, the owner follows Shipping step 6 for its own PR. Check the pre-merge read and the read-back that Shipping step 6 names.
8. **Hold on a third rebase.** If trunk would force a third rebase past merge prep, the owner holds and reports to you, and you sequence the colliding work. Check that the log shows no PR rebased more than twice past merge prep.
9. **A PR is done when it merged at the exact head SHA its verdict names.** An item that stops at owner-green is done at owner-green. When every PR is done, close out as in stack step 7, with a report in place of the handoff. Check that every merged head SHA has a verdict naming it in the log.
10. **In stack step 8, the stand-down also stops merges.** Stop every owner and confirm each stop, so no merge lands after the hold. Check that no PR merged after the hold's time in the log.

**Reply:** catch the user up per the `ketchup` skill: each PR with its link, state, and verdict, what merged and the read-back that confirms it, countersigns and why, open user gates, follow-ups in the log, and the log path.
