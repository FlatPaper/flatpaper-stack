### Autopilot stack

**You own the verdicts, never the PRs. One owner carries each PR from build to green, and no PR goes to the user until a swarm that never wrote its code has proven it. Nothing merges.**

For a queue of changes the user hands off to build and verify unattended ("autopilot", "build the stack, I'll land it", "stack them, don't ship"). A verdict covers one patch, and green CI covers one head.

1. **Pin the queue and the user's gates first.** List the PRs to build, the base branch, and which PRs depend on which. If a Multi-phase plan names this playbook, the queue, gates, and verification boxes come from it. The grant covers only those items. A request to state the plan is not a go. Start a decision log with the show-me-your-work skill before the first spawn, in the main checkout. Only you write it. Arm the heartbeat in step 6 on the go.
2. **Spawn one owner per PR.** Each owner is `subagent_type: "flatpaper-stack:flatpaper-agent"` with `isolation: "worktree"` and `run_in_background: true`, briefed per `../references/subagent-brief.md`. The brief opens with `ROLE: autopilot owner` and the path of this file. Its first step is `git fetch origin && git switch -c <branch> origin/<base>`, because the worktree starts at your HEAD, not at the base. Its FORBIDDEN field allows a rebase of its own branch and a `--force-with-lease=<branch>:<sha>` push pinned to the SHA it last pushed, and forbids `gh pr merge`, `gh pr ready`, auto-merge, and any push to another branch. Record each owner's agent id, branch, start time, and a stuck-after time in the log. An owner that has neither pushed nor reported by the first heartbeat is stuck.

   The owner builds the change and opens a draft PR per `opening-a-pr.md` early, so CI and bots run alongside the work. It proves the change on the real artifact through the `verify-<app>` skill. If its worktree has none, it drives the surface by hand and says so. It never offers to create one. The code is ready only after the `tidy` and `no-comments` commits, so the swarm runs on finished code. It then rebases onto its base, pushes, and reports the code-ready head and its patch-id (`git diff origin/<base>...HEAD | git patch-id --stable`). It reports every later head the same way. Fix rounds stay on that base unless the base conflicts, breaks CI, or lands a change to the same files, because each rebase restarts CI. It runs the repo's checks for the touched paths before each push, pushes each finished unit before starting the next, and on a push it did not make, stops and reports to you. If the PR gate blocks its `gh pr create`, it reports `BLOCKED: pr-gate`, and you ask the user to restart the run with `FLATPAPER_PR_GATE_OFF=1`.
3. **Base each PR on trunk, unless it builds on another PR in the queue.** Independent PRs run in parallel off trunk, so each can land on its own. Spawn a dependent PR's owner only after its parent reports a pushed head, with the parent's branch as its base and the head SHA in the brief. Only the stack root rebases onto trunk. When a parent reports a new head, send it to each child owner with `SendMessage`, or spawn a replacement if the child has finished. The child rebases onto it and reports its new head and patch-id.
4. **Swarm-verify once per PR.** At the code-ready head, fan out verifiers that never wrote the code, per the `swarm` skill. They rerun the gates, prove the load-bearing behavior live on the real surface through the `verify-<app>` skill, and audit the diff against the PR body. Live lanes run one at a time, unless the `verify-<app>` skill gives each worktree its own ports and data. Log which way you ran them. The verdict is not clean without the live lane, and not before you check the receipts in the owner's report.

   After the verdict, a new head with the same patch-id keeps the verdict and needs only green CI. A new patch-id gets one verifier at the new head, unless it brings new behavior, a redesign, or a large new diff, which gets a full swarm again. A wording-only change gets none.

   Block a PR only for a problem you can show: a failing run at the head, or a doc line the PR made wrong. A problem the PR's base already has does not block, unless the PR copies it or newly reaches it. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks. Everything else is a follow-up in the log. Send blocking findings to the PR's owner with `SendMessage`. A finding is not a change of directives, so the owner keeps its brief.
5. **Countersign anything that loosens a gate.** A raised budget, a skipped test, or an allowlist entry needs a verifier's proof and then your own fresh check, because the owner is the one who wants green. A disabled or soft-failed check always comes out. Never give or bypass an approval GitHub enforces.
6. **Audit on a heartbeat.** Arm `/loop` as a long fallback heartbeat, about an hour, because long runs drift and agents stall silently. Its prompt names this file's absolute path and says nothing merges. Agent completion notices are the main wake signal. Each tick re-reads this playbook, records any unreported head or unrecorded agent in the log, and judges every agent by its pushes and commits, not its status text. An agent past its stuck-after time with nothing new is stuck. One waiting on you is not stuck, so answer it. Stop a stuck owner, confirm the stop, and run `git worktree remove --force <its worktree>` so the branch is free. Then spawn a replacement that checks out the branch at its last pushed SHA. A tick that changed something ends with a catch-up per the `ketchup` skill. A tick that changed nothing stays quiet.
7. **Stop at verified and hand off.** A PR is done when its verdict covers its current head and the repo's required checks ran and passed on that head. If CI skips drafts, record that as a user gate in the handoff instead of calling the PR green. When every PR is done, stop the heartbeat and hand the PRs to the user. After the handoff, nobody pushes without the user's go.
8. **Stand down at once on the user's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the user releases it.

**Reply:** catch the user up per the `ketchup` skill: each PR with its link, base, head, and verdict, countersigns and why, open user gates, follow-ups in the log, and the log path.
