### Shipping

**You own what lands. Verify each PR on its own, land only the verified run from the bottom, then keep your hands off the stack.**

For a stack the user asks to land ("land it", "ship the stack", "merge the verified PRs"). Only that explicit request starts this playbook. It grants the verdict comments, the merges, and the lease-pinned pushes below, and nothing else. Babysit (`babysit.md`) ends at merge-ready, and this playbook begins there. A verdict covers one patch, and green CI covers one head.

1. **Verify each PR independently before it lands.** List the stack bottom to top with each PR's number, base, and head from `gh pr view <n> --json number,baseRefName,headRefName,headRefOid`. Each PR needs a verdict of `PASS`, `PASS+NOTES`, or `FAIL` from an agent that did not write its code, because an author checks what it meant to build. A verdict from an Autopilot stack swarm counts if step 3 shows it still describes the code. For each PR without one, spawn a fresh verifier with `subagent_type: "flatpaper-stack:flatpaper-agent"` and `isolation: "worktree"`, briefed per `../references/subagent-brief.md`. It runs the change the way a user would, at the PR's base and at its head, through the project's `verify-<app>` skill, or through the `control-ui` or `control-cli` skill per flatpaper-mode's Driving the app section when the project has none. Run verifiers one at a time, unless the `verify-<app>` skill gives each worktree its own ports and data. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would. Log each verdict with its head SHA and patch-id per the show-me-your-work skill, and post it on its PR with `gh pr comment <n> --body-file <file>`. Check that every PR on the list has a logged verdict, and that the agent id logged with it is not the PR's owner.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one of the run is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. A PR whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it. A PR that waits on an approval GitHub enforces stops the walk like a missing verdict. Never give or bypass that approval. Check that the run has no gap, that its ceiling is named, and that no PR in it reads `REVIEW_REQUIRED` in `gh pr view <n> --json reviewDecision`.
3. **Re-check that each verdict still describes the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Before you trust an older verdict, run `git fetch origin` and compare the patch-id logged with it to `git diff origin/<base>...origin/<branch> | git patch-id --stable`. A match keeps the verdict, and the head needs only green CI. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The changed files still get fresh checks and a review, because the old verdict never saw them. A lane with no build output, such as a dev server, cannot show this, so rerun it. Re-verify anything else that drifted per step 1. Check that each verdict in the run matches its head's patch-id, or has a noise report, a rerun, or a fresh verdict.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR, because a PR whose base is still its parent's branch merges into that branch, not trunk. Mark it ready with `gh pr ready <n>`, because GitHub cannot merge a draft. Wait for its required checks with `gh pr checks <n> --required --watch`, then merge with the repo's strategy flag and the verified head pinned, as in `gh pr merge <n> --squash --match-head-commit <sha>`. The pin makes GitHub refuse the merge if the head moved after step 3. Never pass `--auto` or `--admin`, because each lands a head nobody checked at that moment. Read the PR back with `gh pr view <n> --json state,mergedAt,baseRefName,autoMergeRequest`, because a merge command can report success when a merge queue only queued the PR. Check that `mergeStateStatus` read `CLEAN` or `HAS_HOOKS` right before the merge, so nothing needed `--admin`, and that the PR now reads `MERGED` with trunk as its base and a null `autoMergeRequest`.
5. **Move the next PR onto trunk.** Retarget it with `gh pr edit <n> --base <trunk>`, unless GitHub already did. Run `git fetch origin`. In a worktree on its branch, move its own commits onto the merge result with `git rebase --onto origin/<trunk> <parent's last head>`, then push with `git push --force-with-lease=<branch>:<its head before the move> origin <branch>`. A rebase that conflicts ends the run. Report it, because a resolved conflict is a new patch that needs a fresh verdict. The verdict covers the patch, not its commits, so step 3 decides whether it survives the move. Merge the PR per step 4 once its required checks pass and its verdict survives. Check that its patch-id after the move matches the one its verdict logged, or that step 3 renewed the verdict.
6. **Leave the stack alone while it lands.** Step 5's move is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Wait on checks as Babysit (`babysit.md`) step 11 does, with `--required` added, so the session wakes when they finish. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything. Check that every PR step 5 did not move still has the `headRefOid` on the step 1 list, and that each wait was a check watch, not a sleep loop.
7. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1. Check that no PR above the ceiling merged.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and the read-back that confirms it, and what the next gap needs.
