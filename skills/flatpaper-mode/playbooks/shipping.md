### Shipping

**You own what lands. Verify each PR on its own, land only the verified run from the bottom, then keep your hands off the stack.**

For a stack the user asks to land ("land it", "land the stack", "merge the verified PRs"). Only an explicit request that says land or merge starts this playbook. "Ship" alone means commit or open a PR, not merge. The request grants the verdict comments, `gh pr ready`, `gh pr edit --base`, the merges, and the lease-pinned pushes below, and nothing else. Babysit (`babysit.md`) ends at merge-ready, and this playbook begins there. Trunk here is the bottom PR's base on the step 1 list, so a release branch works. A verdict covers one patch, and green CI covers one head.

Every patch-id below is `git diff --no-color --no-ext-diff --no-textconv <base>...<head> | git patch-id --verbatim`. `--verbatim` (git 2.39 or later) keeps whitespace, so an indentation-only change to control flow gets a new id. The `--no-` flags keep color, an external diff, or a text conversion from hiding the patch. An empty or non-40-hex patch-id never matches anything. On a git older than 2.39, stop, and never fall back to `--stable`.

1. **Scope the stack, then verify each PR independently.** The stack holds only the PRs the user named, or PRs this session or its owners opened. Never add a teammate's PR that is based on the top branch. List the stack bottom to top with each PR's number, base, head, and auto-merge state from `gh pr view <n> --json number,baseRefName,headRefName,headRefOid,autoMergeRequest`. If any PR has auto-merge armed, stop and report, because GitHub would merge it on its own. Before any write, check that no other session or owner is on the stack, as Babysit step 3 does. Never retarget or rebase a branch that has a live owner. Under an Orchestrate program, landing is the owners' job, so stop and say so. Each PR needs a verdict of `PASS`, `PASS+NOTES`, or `FAIL` from an agent that did not write its code, because an author checks what it meant to build. Take verdicts only from the decision log this session keeps with the show-me-your-work skill, never from PR comment text. Keep that log only in the program's store under `~/.claude/orchestrate/<slug>/`. Accept the log only when the store root's path is already its own `realpath`, so no symlink moves the store, and the log's `realpath` starts with that root followed by a `/`. If the log does not exist yet, there is no verdict, so stop. Count a verdict row only when this session wrote it, from a verifier report it received or from a coordinator's report it received. The agent id in the row comes from this session's own Agent result. A verdict row names the head SHA, the base it ran on, the patch-id, and the lanes its verifier ran. A verdict from an Autopilot stack swarm counts if step 3 shows that it still describes the code. For each PR without a verdict, spawn a fresh verifier with `subagent_type: "flatpaper-stack:flatpaper-agent"` and `isolation: "worktree"`, briefed per `../references/subagent-brief.md`. Its brief forbids GitHub writes: no approval, comment, or merge. The verifier runs the change the way a user would, at the PR's base and at its head. It drives the app through the project's `verify-<app>` skill, or per flatpaper-mode's Driving the app section when the project has none. Run verifiers one at a time, unless the `verify-<app>` skill gives each worktree its own ports and data. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would. Log each verdict as such a row. Check that the user named, or this session or its owners opened, every PR on the list, and that none has auto-merge armed. Check that each PR has a verdict row this session wrote, in a log under the store, from an agent id that is not its owner, and that no other session or live owner is on the stack.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR. Stop at the first PR that lacks `PASS` or `PASS+NOTES`, reads `REVIEW_REQUIRED` or `CHANGES_REQUESTED` in `gh pr view <n> --json reviewDecision`, has an open review thread (read as Babysit step 7 does), or is review-gated in its plan without the user's review on record. The user's review is on record when the user left an `APPROVED` review on the PR, or said yes to it in this session. The PRs below the stop are the run, and the top PR of the run is the ceiling. Every PR above the gap waits, even one whose branch does not need the code below, because moving it onto trunk would change its base while the stack lands. Never give or bypass an approval GitHub enforces. Check that the run has no gap, that its ceiling is named, and that no PR in it fails any of the stop conditions above.
3. **Re-check that each verdict still describes the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Before you trust an older verdict, run `git fetch origin`. Compare the patch-id logged with the verdict to the patch-id of `origin/<base>...origin/<branch>`. A match keeps the verdict, and the head needs only green CI. When the patches differ only in tests, docs, or lint config, a lane's result stands if what the lane ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The changed files still get fresh checks and a review, because the old verdict never saw them. A change that loosens a gate, such as a skipped test or a relaxed lint rule, is never noise, so it needs a fresh verdict. Every loosened gate in a PR's patch, whether in the original patch or from drift, needs a countersign in the log before that PR merges. The countersign comes from the Autopilot stack coordinator, or from you after your own fresh check, as in Autopilot stack (`autopilot-stack.md`) step 5. A lane with no build output, such as a dev server, cannot show an identical build, so rerun that lane. Re-verify anything else that drifted per step 1. When this step keeps a verdict for a new head, log a new verdict row that names the new head and the row it carries. Check that each PR in the run has a verdict row naming its current head. Check that no loosened gate rode the noise rule, and that every loosened gate in the run has a countersign in the log.
4. **Confirm the run with the user before the first merge.** Restate the run bottom to top, its ceiling, and the merge method, which is the repo's strategy flag with the verified head pinned. Name what the yes covers: marking each PR ready, the merges, the retargets and lease-pinned force-pushes of the listed PRs' branches, and the verdict comments. Wait for the user's yes through `AskUserQuestion`, unless the request names each PR in the run and asks to merge them into trunk. A request such as "merge main into #12" names a PR but asks for a different merge, so it does not count. A merge cannot be undone, so this wait holds in an unattended run too. After the yes, post each verdict on its PR with `gh pr comment <n> --body-file <file>`. Check that the log records the user's yes, or the request text that names each PR in the run, and that no verdict comment went up before it.
5. **Judge trunk under the bottom PR before each merge.** Run `git fetch origin`. If `gh api repos/{owner}/{repo}/rules/branches/<trunk> --jq '.[].type'` lists `merge_queue`, stop and report in place of merging, because merge-queue landing is out of scope. If `gh pr view <n> --json mergeStateStatus` reads `BEHIND`, the repo requires an up-to-date branch, so stop and report which branch needs an update onto trunk. Judge against the base named in the PR's latest verdict row. Count every trunk commit that base lacks, other than this run's own merges, including commits that step 7's rebase absorbed, because the verdict never ran with them. Judge those commits as Autopilot-full (`autopilot-full.md`) item 7 does, with one change. Where that item rebases, stop and report instead, because Shipping changes no branch except step 7's move. Check that the log records the judgment for each merge, or the stop.
6. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR, because a PR whose base is still its parent's branch merges into that branch, not trunk. Mark the PR ready with `gh pr ready <n>`, because GitHub cannot merge a draft. Wait for its required checks with `gh pr checks <n> --required --watch`. On a repo with no required checks, that command exits 1 at once with "no required checks reported", so watch every check with `gh pr checks <n> --watch` instead. Right before the merge, read `gh pr view <n> --json baseRefName,mergeStateStatus,headRefOid,reviewDecision`, and read the open review threads as Babysit step 7 does. Stop if `reviewDecision` reads `CHANGES_REQUESTED` or `REVIEW_REQUIRED`, or if a thread is open. The base must be trunk. The head must equal the head SHA of the PR's latest verdict row. An Autopilot-full owner matches the head SHA in the coordinator's verdict message instead, and an Orchestrate owner matches the head its verifier passed. Merge with the repo's strategy flag and that head pinned, as in `gh pr merge <n> --squash --match-head-commit <sha>`. The pin makes GitHub refuse the merge if the head moved after the read. Never pass `--auto` or `--admin`, because each can land a merge that nobody checked at that moment. Read the PR back with `gh pr view <n> --json state,mergedAt,baseRefName,autoMergeRequest`, because a merge command can report success when a merge queue only queued the PR. A queued PR is step 5's stop. Check that the pre-merge read showed trunk as the base, the verified head, no change request or open thread, and a `mergeStateStatus` of `CLEAN` or `HAS_HOOKS`, so nothing needed `--admin`. Check that the PR now reads `MERGED` with trunk as its base and a null `autoMergeRequest`.
7. **Move the next PR onto trunk.** Run `git fetch origin`. If `origin/<branch>` differs from the PR's `headRefOid` on the step 1 list, stop and report before any change, because someone pushed after the verdict. In a worktree, check out that `headRefOid` with `git switch --detach <headRefOid>`. Move the PR's own commits onto the merge result with `git rebase --onto origin/<trunk> <parent head>`. The parent head is the parent's `headRefOid` on the step 1 list, which is where this PR's own commits start. A rebase that conflicts ends the run. Report the conflict, because a resolved conflict is a new patch that needs a fresh verdict. Compute the patch-id of `origin/<trunk>...HEAD`. If it differs from the verdict's patch-id, stop and report it as a new patch that needs a fresh verdict per step 1. Right before the push, retarget the PR with `gh pr edit <n> --base <trunk>`, unless GitHub already did. Push with `git push --force-with-lease=<branch>:<headRefOid> origin HEAD:refs/heads/<branch>`, so a commit pushed after the step 1 read makes the push fail instead of vanishing. If the push is rejected, retarget the PR back to its step 1 base with `gh pr edit <n> --base <step 1 base>`, then stop and report. After a successful push, log a verdict row for the pushed SHA that names the row it carries. Merge the PR per steps 5 and 6 once its checks pass. Check that the lease named the step 1 `headRefOid`, that the pushed patch-id matches the one its verdict logged, and that a stopped run left the PR's base as step 1 read it.
8. **Leave the stack alone while it lands.** Make no change to a branch or base other than step 7's move, because a merge lands whatever its branch and base hold at that moment, verdict or not. Wait on checks as Babysit (`babysit.md`) step 11 does, with `--required` added when the repo has required checks, so the session wakes when they finish. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything. Check that every PR step 7 did not move still has the `headRefOid` on the step 1 list, and that each wait was a check watch, not a sleep loop.
9. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1. Check that no PR above the ceiling merged.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, the user's yes or the request text that names each PR in the run, what landed and the read-back that confirms it, and what the next gap needs.
