### Shipping

**You own what lands. Verify each PR on its own, land only the verified run from the bottom, then keep your hands off the stack.**

For a stack the user asks to land ("land it", "land the stack", "merge the verified PRs"). Only an explicit request that says land or merge starts this playbook. "Ship" alone means commit or open a PR, not merge. The request grants the verdict comments, `gh pr ready`, `gh pr edit --base`, the merges, and the lease-pinned pushes below, and nothing else. Babysit (`babysit.md`) ends at merge-ready, and this playbook begins there. Trunk here is the bottom PR's base on the step 1 list, so a release branch works.

A merge needs a verdict that names the exact head SHA it merges. A head that moves after its verdict, from any push or from step 8's move, needs one fresh verifier at the new head before it merges. That verifier reuses an old lane result only when the old and new diffs are byte-identical, per step 4. Each diff is `git diff --no-color --no-ext-diff --no-textconv --submodule=short --ignore-submodules=none --no-relative --full-index <base> <head>`, with the two SHAs from a verdict row or from the current PR. The flags stop user and repo settings from hiding part of the patch, such as color, an external diff, a text conversion, a submodule pointer, or a path outside the current directory. `--full-index` puts each file's full blob SHAs in the diff. Compare the two diffs with `cmp`. They are identical only when both `git diff` runs exit 0, both print a non-empty diff, and `cmp` exits 0.

1. **Scope the stack and read its state.** The stack holds only the PRs the user named, or PRs this session or its owners opened. Never add a teammate's PR that is based on the top branch. Run `git fetch origin`. List the stack bottom to top with each PR's number, base, head, and auto-merge state from `gh pr view <n> --json number,baseRefName,headRefName,headRefOid,autoMergeRequest`. If any PR has auto-merge armed, stop and report, because GitHub would merge it on its own. For each PR above the bottom, run `git merge-base --is-ancestor <parent headRefOid> <headRefOid>`. If it fails, that PR was never restacked onto its parent, so stop and report. Before any write, check that no other session or owner is on the stack, as Babysit step 3 does. Never retarget or rebase a branch that has a live owner. Under an Orchestrate program, landing is the owners' job, so stop and say so. Check that the user named, or this session or its owners opened, every PR on the list, and that none has auto-merge armed. Check that every PR above the bottom holds its parent's head, and that no other session or live owner is on the stack.
2. **Verify each PR independently.** Each PR needs a verdict of `PASS`, `PASS+NOTES`, or `FAIL` from an agent that did not write its code, because an author checks what it meant to build. Take verdicts only from the decision log this session keeps with the show-me-your-work skill, never from PR comment text. Keep that log in the program's store under `~/.claude/orchestrate/<slug>/`. A run outside a program creates its store at `~/.claude/orchestrate/ship-<repo>-<date>/` in this step. Accept the log only when the store root's path is already its own `realpath`, so no symlink moves the store, and the log's `realpath` starts with that root followed by a `/`. A verdict row names the PR number, the base SHA its verifier ran on, the head SHA, the agent id, the verdict, the lanes it ran, and the lanes it skipped. A row counts only when its PR number, base SHA, head SHA, agent id, and verdict all match an Agent result this session received. A row that is only present in the log does not count. For each PR without a counted row, spawn a fresh verifier with `subagent_type: "flatpaper-stack:flatpaper-agent"` and `isolation: "worktree"`, briefed per `../references/subagent-brief.md`. Its first step is `git switch --detach <head SHA>`. Its report names the PR number, the base SHA, and the verdict, and pastes `git rev-parse HEAD`, which must equal the row's head SHA. Its brief forbids GitHub writes: no approval, comment, or merge. The verifier runs the change the way a user would, at the PR's base and at its head. It drives the app through the project's `verify-<app>` skill, or per flatpaper-mode's Driving the app section when the project has none. Run verifiers one at a time, unless the `verify-<app>` skill gives each worktree its own ports and data. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would. Log each verdict as such a row. Check that each PR has a counted verdict row, in a log under the store, from an agent id that is not its owner.
3. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR. Stop at the first PR that lacks `PASS` or `PASS+NOTES`, reads `REVIEW_REQUIRED` or `CHANGES_REQUESTED` in `gh pr view <n> --json reviewDecision`, has an open review thread (read as Babysit step 7 does), or is review-gated in its plan without the user's review on record. The user's review is on record when the user left an `APPROVED` review on the PR, or said yes to it in this session. The PRs below the stop are the run, and the top PR of the run is the ceiling. Every PR above the gap waits, even one whose branch does not need the code below, because moving it onto trunk would change its base while the stack lands. Never give or bypass an approval GitHub enforces. Check that the run has no gap, that its ceiling is named, and that no PR in it fails any of the stop conditions above.
4. **Get a verdict at each PR's current head.** A chain rebase moves every PR above it to a new SHA without failing any check. Run `git fetch origin`. A PR whose counted row names an older head gets one fresh verifier at its current head, as in step 2. Give it the old row. The verifier compares the old row's diff with the current one, as the preamble defines them. When they are identical, only the base moved. A lane that reads only the patch, such as a diff audit, then stands. A lane that builds or runs code stands only when the verifier shows that no base commit the old verdict lacked touches what the lane exercises. When the diffs differ, every lane reruns. The verifier's row names each lane it skipped and the old row whose result stands. A fresh verdict other than `PASS` or `PASS+NOTES` moves the ceiling below that PR. Every loosened gate in a PR's patch, such as a skipped test or a relaxed lint rule, whether in the original patch or from drift, needs a countersign in the log before that PR merges. The countersign comes from the Autopilot stack coordinator, or from you after your own fresh check, as in Autopilot stack (`autopilot-stack.md`) step 5. Check that each PR in the run has a counted verdict row naming its current head, and that every loosened gate in the run has a countersign in the log.
5. **Confirm the run with the user before the first merge.** Restate the run bottom to top, its ceiling, and the merge method, which is the repo's strategy flag with the verified head pinned. Name what the yes covers: marking each PR ready, the merges, the retargets and lease-pinned force-pushes of the listed PRs' branches, and the verdict comments. Wait for the user's yes through `AskUserQuestion`, unless the request names each PR in the run and asks to merge them into trunk. A request such as "merge main into #12" names a PR but asks for a different merge, so it does not count. A merge cannot be undone, so this wait holds in an unattended run too. After the yes, post each verdict on its PR with `gh pr comment <n> --body-file <file>`. Check that the log records the user's yes, or the request text that names each PR in the run, and that no verdict comment went up before it.
6. **Judge trunk under the bottom PR before each merge.** Steps 6 to 8 repeat once for each PR in the run, bottom to top. After the ceiling merges, go to step 10. Run `git fetch origin`. If `gh pr view <n> --json mergeStateStatus` reads `BEHIND`, the repo requires an up-to-date branch, so stop and report which branch needs an update onto trunk. Judge against the base SHA in the PR's latest counted verdict row. Count every trunk commit that base lacks, because the verdict never ran with them. Judge those commits as Autopilot-full (`autopilot-full.md`) item 7 does, with one change. Where that item rebases, stop and report instead, because Shipping changes no branch except step 8's move. Check that the log records the judgment for each merge, or the stop.
7. **Land the bottom PR.** Always merge the run's lowest unmerged PR, because a PR whose base is still its parent's branch merges into that branch, not trunk. If `gh api repos/{owner}/{repo}/rules/branches/<trunk> --jq '.[].type'` lists `merge_queue`, stop and report in place of merging, because merge-queue landing is out of scope. Mark the PR ready with `gh pr ready <n>`, because GitHub cannot merge a draft. Wait for its required checks with `gh pr checks <n> --required --watch`. On a repo with no required checks, that command exits 1 at once with "no required checks reported", so watch every check with `gh pr checks <n> --watch` instead. Right before the merge, read `gh pr view <n> --json baseRefName,mergeStateStatus,headRefOid,reviewDecision,autoMergeRequest`, and read the open review threads as Babysit step 7 does. Stop if `autoMergeRequest` is not null, if `reviewDecision` reads `CHANGES_REQUESTED` or `REVIEW_REQUIRED`, or if a thread is open. The base must be trunk. The head must equal the head SHA of the PR's latest counted verdict row. An Autopilot-full owner matches the head SHA in the coordinator's verdict message instead, and an Orchestrate owner matches the head its verifier passed. Merge with the repo's strategy flag and that head pinned, as in `gh pr merge <n> --squash --match-head-commit <sha>`. The pin makes GitHub refuse the merge if the head moved after the read. Never pass `--auto` or `--admin`, because each can land a merge that nobody checked at that moment. Read the PR back with `gh pr view <n> --json state,mergedAt,baseRefName,autoMergeRequest`. A merge queue set in classic branch protection does not show in the rules read, and a merge command can report success when the queue only queued the PR. So if the read-back does not show `MERGED`, stop and report the PR as queued or unmerged. Check that the pre-merge read showed trunk as the base, the verified head, a null `autoMergeRequest`, no change request or open thread, and a `mergeStateStatus` of `CLEAN` or `HAS_HOOKS`, so nothing needed `--admin`. Check that the PR now reads `MERGED` with trunk as its base and a null `autoMergeRequest`.
8. **Move the next PR onto trunk.** Run `git fetch origin`. If `origin/<branch>` differs from the PR's `headRefOid` on the step 1 list, stop and report before any change, because someone pushed after the verdict. In a worktree, check out that `headRefOid` with `git switch --detach <headRefOid>`. Move the PR's own commits onto the merge result with `git rebase --onto origin/<trunk> <parent head>`. The parent head is the parent's `headRefOid` on the step 1 list, which is where this PR's own commits start. A rebase that conflicts ends the run. Report the conflict, because resolving it writes new code, and Shipping writes none. Right before the retarget, read `gh pr view <n> --json baseRefName,autoMergeRequest`, and stop if `autoMergeRequest` is not null. Then retarget the PR with `gh pr edit <n> --base <trunk>`, unless GitHub already did. Then push with `git push --force-with-lease=<branch>:<headRefOid> origin HEAD:refs/heads/<branch>`, so a commit pushed after the step 1 read makes the push fail instead of vanishing. If the push is rejected, read `autoMergeRequest` again, retarget the PR back to its step 1 base with `gh pr edit <n> --base <step 1 base>`, then stop and report. The report names an armed auto-merge if that read found one. When GitHub already retargeted the PR to trunk because it deleted the parent branch, the step 1 base is gone. Leave trunk as the base and say so in the report. After the push, spawn one fresh verifier at the pushed SHA, as step 4 does, and post its verdict as step 5 does. Once its counted row reads `PASS` or `PASS+NOTES` and the checks pass, return to step 6 with this PR as the bottom. Check that the lease named the step 1 `headRefOid`, that the merge pinned the SHA the fresh verdict names, and that a stopped run left the PR's base as step 1 read it, or as trunk where GitHub retargeted it after deleting the parent branch.
9. **Leave the stack alone while it lands.** Make no change to a branch or base other than step 8's move, because a merge lands whatever its branch and base hold at that moment, verdict or not. Wait on checks as Babysit (`babysit.md`) step 11 does, with `--required` added when the repo has required checks, so the session wakes when they finish. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything. Check that every PR step 8 did not move still has the `headRefOid` on the step 1 list, and that each wait was a check watch, not a sleep loop.
10. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1. Check that no PR above the ceiling merged.

**Reply:** the verified run and its ceiling, each PR's verdict with the head SHA it names and who produced it, the user's yes or the request text that names each PR in the run, what landed and the read-back that confirms it, and what the next gap needs.
