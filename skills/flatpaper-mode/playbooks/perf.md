### Perf

**You own the measurement story. Every kept change ties to a number. Reading source is not measuring.**

For a one-off speedup or regression fix against a measured number. A sustained climb on one metric toward a target, over many attempts, is Hillclimb (`playbooks/hillclimb.md`). Steps 1 to 4 are the harness steps. Hillclimb runs them too, for any metric.

1. Pick a case that reproduces the user's complaint, with realistic data size, state, and concurrency. If no case reproduces it, fix the repro first. Fix one metric, the direction that counts as better, and the target. For a deterministic metric, such as a byte count, also fix the minimum gain worth keeping, so a 1-byte win does not count. Use the user's numbers when given. The log directory is `"$(git rev-parse --git-common-dir)/flatpaper/<branch>"`, outside the tree. Run every command that names it from the repo root, starting with `mkdir -p "$(git rev-parse --git-common-dir)/flatpaper/<branch>/runs"`. Open the decision log there as `decisions.tsv` with the `show-me-your-work` skill. Log one row per attempt. The decision cell holds the hypothesis and the change, and the why cell holds its mechanism. The evidence cell points at the attempt's harness output, saved under `runs/` in the log directory. The result cell holds `kept` or `reverted`, the before and after medians with their ranges, the delta written as `delta -16.6%`, and the gate result. The check is the case, the metric, and the target in the log's first row.
2. Build the harness, prove it is sensitive, then freeze it. Run contrasting workloads and confirm the target case shows the symptom while easier cases separate. Make it print an error count and a count of the work done. Build its end-to-end case from the `verify-<app>` skill's Launch and Drive recipe. With no such skill, drive a UI with the `control-ui` skill or an interactive CLI with the `control-cli` skill. Time a batch CLI with a script that runs the command as a subprocess, and keep the driver for the end-to-end case. Once frozen, one command emits the metric. The harness files are the harness script, its fixtures, its golden outputs, and the gate tests. When the metric is the output itself, as with a minifier's byte count, an invariant check such as a round trip replaces the golden outputs. Record their checksums from the repo root with `shasum -a 256 <files> > "$(git rev-parse --git-common-dir)/flatpaper/<branch>/harness.sha256"`, and never change those files after that. The check is that command's output, where the target case's number separates from the easier cases' numbers, and `harness.sha256` on file.
3. Record the baseline. Check machine load first (`uptime`, plus `nproc` on Linux or `sysctl -n hw.ncpu` on macOS). Take the median of 5 or more runs with the range, never one run. Record a green run of the regression gate (the tests that must keep passing). Answer all seven questions of the `benchmark-checklist` skill for the baseline from a run, not from the code. Write the answers to a file in the log directory, and point at it from the baseline row. The check is the baseline row, with the median, the range, the gate result, and the checklist answers.
4. Measure every attempt with the keep rule. First run `shasum -a 256 -c "$(git rev-parse --git-common-dir)/flatpaper/<branch>/harness.sha256"` from the repo root. Commit the attempt, so `HEAD~1` is the before side. Measure before and after again for each attempt, 5 or more runs per side, alternating them (before, after, before, after). A deterministic metric needs one run per side, and its gain must reach the minimum from step 1. Keep both builds runnable, for example with a second worktree at the parent commit (`git worktree add <dir> HEAD~1`). Keep the change only when the before and after ranges do not overlap, the after side is better, and the gate stays green. Otherwise revert it in full with `git reset --hard HEAD~1`, so the history holds only kept commits. Revert any win that breaks behavior. Whoever commits an attempt stages only its files (`git add <files>`, never `-A`) and makes one commit per kept change. Per attempt, answer three `benchmark-checklist` questions from the harness output: errors, repeatability, and whether the work ran. Save the answers with that output under `runs/`. For the final number, answer all seven. The check is a matching checksum before each measurement and one log row per attempt.
5. Ground each hypothesis. Run the `how` skill over the hot path. If you cannot spawn its explorers, trace the hot path by hand and log that. Name the mechanism each hypothesis changes ("defer X off the boot path because it blocks first paint"). Don't claim a ceiling you have not measured. Try the mantras in order, cheapest first:
   1. Don't do it. Stop work whose result nothing uses instead of making it cheaper.
   2. Do it, but don't do it again.
   3. Do it less.
   4. Do it later.
   5. Do it when they're not looking.
   6. Do it concurrently.
   7. Do it cheaper.

   Skip a mantra that does not apply to the workload, such as "do it later" for a batch CLI, and log the skip. Stop at the first mantra that meets the target. The check is each hypothesis with its mechanism and its mantra.
6. Plan the fix from the profile or trace. If it crosses a function boundary, run the `architect` skill first. Make one change, and measure it per step 4. Verify each attempt before you try the next (sequence verifiable units). The check is the post-fix median and range next to the baseline.
7. Compare the artifacts, not only the headline number. Parse the baseline and post-fix traces or profiles into sqlite, for example with `sqlite3` and `json_each(readfile('<trace>.json'))`, and diff them in one query. "Inconclusive" or a number from the wrong surface is not a pass. Flag it. The check is the query and its output.
8. Stop at the target. If the fixes so far miss it and more attempts are needed, switch to Hillclimb and keep this harness, baseline, and log. If the target looks out of reach, say so with the limiter. Never relax the target to meet it. The check is the step 1 target, unchanged, and either met or the switch to Hillclimb stated in one line.

**Reply:** the metric and target, baseline to post-fix as median and range with the percent delta, the limiter, each kept change on one line, the artifact paths with the sqlite diff, and the decision log path.
