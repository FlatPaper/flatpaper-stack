### Visual parity

**You own pixel-exact equivalence. The baseline is the spec, and you never edit it.** An image diff decides equivalence, not your eye.

For a migration or refactor that must not change how the UI looks ("match the old UI pixel for pixel", "migrate without visual change", "visual regression"). A change meant to alter the look is Feature.

1. Build the harness before any migration. It is a script that screenshots each component in each of its states, through the project's `verify-<app>` skill or, without one, the `control-ui` skill's `cdp.mjs --screenshot`. One run writes one PNG per component state into a directory it is given. When you match two implementations, it screenshots both. No harness means no parity claim, so this step blocks the rest. The check is the script and one PNG per state.
2. Pin what makes screenshots nondeterministic. Set the page size with `--viewport <W>x<H>`, which also fixes the scale at 1. In `--eval`, add a style that turns off animations, transitions, and the text caret, then `await document.fonts.ready`. `--eval` runs after the page loads, so pin time and random data in the fixture the page renders, such as a fixed clock and seeded data. Take every screenshot on one machine with one Chrome build, because system fonts and rendering differ across both. Run the harness twice on unchanged code and diff each pair. The check is a zero diff on every pair.
3. Capture the baseline from the code before the migration, for example in a worktree at the base commit. Record a `shasum -a 256` of every baseline file. Prove that the diff catches a change: seed one small visual change, such as 1px of padding, confirm that `cdp.mjs diff` exits 1 on that state, then revert it. The check is the checksums on file and the seeded change caught.
4. Hold the anti-shortcut clauses. Never change the harness, its pins, or the baseline during the migration. Never restructure a component to make a diff pass. If the harness or the baseline looks wrong, stop and ask the user. Do not edit it. The check is baseline checksums that still match before each verdict.
5. Migrate one component at a time, shared primitives first. The primitives are a blocking phase: a component that uses one waits until it passes step 6. To run components in parallel, give each one an owner: `subagent_type: "flatpaper-stack:flatpaper-agent"` with `isolation: "worktree"`, briefed per `../references/subagent-brief.md`. Owners' dev servers share ports, so their harness runs go one at a time, unless the `verify-<app>` skill gives each worktree its own ports and data. The check is every primitive passing before a component that uses it starts.
6. Verify each component against its baseline. Run the harness for its states, then `cdp.mjs diff <baseline.png> <new.png> --out <delta.png>` for each state. A differing pixel or a size mismatch exits 1, and that is a fail. Investigate the delta. Read the `--out` image, where changed pixels are red, and find the element under them. Compare its computed style in both builds with `--eval`, for example `getComputedStyle(document.querySelector("<css>")).padding`. Fix the migrated code, not the baseline. Run `/loop` per component, with the harness and the diff as its check, until every state of that component diffs to zero. The check is `0 of <total> pixels differ` and exit 0 for every state.
7. Open one PR per component or per safe batch, per `opening-a-pr.md`, with the diff command and its result under Verification. The check is one PR per component or batch, each with its diff result.

**Reply:** the components migrated, each one's diff result, the harness and baseline paths, the checksum recheck, and what is left.
