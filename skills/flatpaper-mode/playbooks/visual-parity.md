### Visual parity

**You own pixel-exact equivalence. The baseline is the spec, and you never edit it.** An image diff decides equivalence, not your eye.

For a migration or refactor that must not change how the UI looks ("match the old UI pixel for pixel", "migrate without visual change", "visual regression"). A change meant to alter the look is Feature.

1. Build the harness before any migration. It is a script that screenshots each component in each of its states and writes one PNG per state into a directory it is given. It drives the page as the Driving the app section of `../SKILL.md` says, which starts with the project's `verify-<app>` skill. When that section falls back to the `control-ui` skill, the harness calls its `cdp.mjs`.
   - The harness takes the build root as an argument, so one harness runs both the base build and the migrated build. Keep it out of the tree the migration edits. Commit it in its own directory, or run it from the working tree against a worktree at the base commit.
   - Each state gets its own shot. Give each state its own URL, or hide its siblings with `--eval` before `--screenshot`. The URL or selector that isolates a state is part of the contract, so the migrated code keeps it.
   - When you match two implementations, the harness screenshots both.

   No harness means no parity claim, so this step blocks the rest. The check is the script and one PNG per state.
2. Pin what makes screenshots nondeterministic.
   - **Size.** Pass `--viewport <W>x<H>`, which also fixes the scale at 1.
   - **Motion and fonts.** In `--eval`, add a style with `*, *::before, *::after { animation: none !important; transition: none !important; caret-color: transparent !important; }`, then `await document.fonts.ready`. The style hides the animations themselves, so check them in a separate run without it. Read `animationName`, `animationDuration`, and `animationTimingFunction` from `getComputedStyle` with `--eval` on each animated element, in both builds, and compare the values.
   - **Time and random data.** `cdp.mjs` has no option to run a script before the page loads, and `--eval` runs after the load. Pin time and random data in the fixture the page renders, such as a fixed clock and seeded data. When the page has no fixture, add a test hook to the base code, such as a `?now=` query parameter, before you capture the baseline. The migrated code keeps the hook.
   - **Machine.** Take every screenshot on one machine with one Chrome build. Record the build next to the baseline, for example the output of `"$CHROME" --version`.

   Run the harness twice on unchanged code and diff each pair. The check is a zero diff on every pair.
3. Capture the baseline from the code before the migration, in a worktree at the base commit. Record a `shasum -a 256` of every baseline file and every harness file in one checksum file. Then prove that the diff catches a change. In the base worktree, seed one small visual change, such as 1px of padding, run the harness, and diff its output against the baseline. Confirm that `cdp.mjs diff` exits 1 on that state, then revert the change. The check is the checksum file, the recorded Chrome build, and the seeded change caught.
4. Hold the anti-shortcut clauses. Never change the harness, its pins, or the baseline during the migration. Never restructure a component to make a diff pass. If the harness or the baseline looks wrong, stop and ask the user, and do not edit either one. In an unattended run or a subagent, stop that component and report `BLOCKED` with the reason. The check is `shasum -a 256 -c <checksum file>` passing for the harness and the baseline before each verdict.
5. Migrate one component at a time, starting with the shared building blocks that other components use, such as buttons and inputs. They are a blocking phase. A component that uses a shared block waits until that block passes step 6. To run components in parallel, give each one an owner. Spawn it with `subagent_type: "flatpaper-stack:flatpaper-agent"` and `isolation: "worktree"`, briefed per `../references/subagent-brief.md`. Owners' dev servers share ports, so their harness runs go one at a time, unless the `verify-<app>` skill gives each worktree its own ports and data. The check is every shared block passing before a component that uses it starts.
6. Verify each component against its baseline. Run the harness on the migrated build. Then loop over every baseline PNG and run `cdp.mjs diff <baseline.png> <new.png> --out <delta.png>` on it and its new counterpart. Any nonzero exit fails the component. A differing pixel or a size mismatch exits 1, and a missing file exits 2. Run step 2's animation check on the component too. Investigate each delta. Read the `--out` image, where changed pixels are red, and find the element under them. Compare its computed style in both builds with `--eval`, for example `getComputedStyle(document.querySelector("<css>")).padding`. Fix the migrated code, not the baseline. Repeat the change, the harness run, and the diff until every state of the component diffs to zero. In an unattended run, `/loop` only wakes the session between rounds, as in `autonomous-run.md`. The check is `0 of <total> pixels differ` and exit 0 for every state, and animation values that match the base build.
7. Open one PR per component or per safe batch, per `opening-a-pr.md`, with the diff command and its result under Verification. The check is one PR per component or batch, each with its diff result.

**Reply:** the components migrated, each one's diff result, the harness and baseline paths, the checksum recheck, the animation check, and what is left.
